## Resolved Important — paragraph Enter copied continuation indentation into a new code block

Location: `web/src/editor/commands.ts`, the paragraph branch and `nextIndent` calculation.

Concrete input: live mode, source `Alpha\n    BetaTail`, collapsed selection at UTF-16 offset **14**, between `Beta` and `Tail`. This is one ordinary top-level paragraph: four-space indentation on a continuation line does not interrupt a paragraph. The configured renderer's paragraph rule explicitly continues over such a line (`node_modules/markdown-it/dist/markdown-it.mjs:2356–2357`), so `isOrdinaryParagraphRange` accepts this caret.

Before the boundary fix, the paragraph branch inserted `\n\n` **plus the current line's four spaces**, producing:

```text
Alpha
    Beta

    Tail
```

After the blank separator, `    Tail` starts an indented code block; the renderer's code rule accepts indentation of four columns at block start (`node_modules/markdown-it/dist/markdown-it.mjs:1636–1655`). The defect combined the new paragraph separator with inherited continuation indentation; the previous single LF kept the continuation in the same paragraph. Tab-indented continuations were affected too.

**Closure:** `nextIndent` now drops inherited indentation when `paragraph` is true and `columns(indent) >= 4`. The existing column calculation uses four-column tab stops, covering four spaces, a tab, and mixed space/tab prefixes. For the original offset-14 split, the insertion is now exactly `\n\n`, leaving `Tail` as prose. True code and source-mode fallback have `paragraph === false` and retain their single-LF insertion and indentation. The original guard for a split inside leading indentation remains, and the patch/EOL/history path is unchanged.

`review-boundaries-red.log` records three failing indentation variants (`"    "`, `"\t"`, `" \t"`). The new tests split at continuation EOF, assert the exact inserted source, undo to original BOM/CRLF bytes, redo, type `NEW`, and require `<p>NEW</p>` with no `<pre>`. All pass in `review-boundaries-green.log`. The original mid-line example is additionally covered by source reasoning through the same `nextIndent` branch, rather than claimed as an executed test.

## Resolved Important — selecting an empty separator's LF hid the selected row

Location: `web/src/live/decorations.ts`, the new `activeGap` predicate and gap filter.

Concrete input: live mode, `Alpha\n\nBeta`, caret at **6** on the empty separator. The row initially reveals. Extend the selection by one character to **[6, 7)**, selecting that empty line's LF (for example Shift-Right), or use the reversed selection with the same range.

Before the boundary fix, the own-line check converted the gap from `[6,7)` to `{from:6,to:6}`, because the empty line's `line.to` equals its start. For a nonempty selection, `isActive` required `r.from < span.to && r.to > span.from`; `6 < 6` was false. The selected separator consequently received `cm-live-gap`, with zero height and hidden visibility, and disappeared when its newline was selected.

**Closure:** `activeGap` now uses the own-line end only for collapsed ranges. Nonempty selections and composition ranges intersect the full gap span, including its LF. Consequently `[6,7)` reveals the separator, while a collapsed caret at 7 does not activate the preceding empty row. CodeMirror's normalized selection `from/to` handles both selection directions. Quote-marker gaps retain the existing `isActive` behavior; persistent extra rows and spacing calculations are unchanged.

`review-boundaries-red.log` records the selected-LF assertion receiving `cm-live-gap` instead of `cm-live-blank`. The new test checks both `[anchor:6,head:7]` and the reverse, requiring the visible class and rejecting the hidden class. These pass in `review-boundaries-green.log`, along with the existing collapsed-neighbor controls. Composition uses the same predicate by inspection; this focused test does not simulate an IME session.
