# Git 分支与发布流

本仓库长期维护 `dev` 与 `main` 两条活动主线。开发线由原 `rewrite/from-zero` 原地改名为 `dev`，提交历史保持不变。`main` 作为默认分支呈现已集成的发布版本；`dev` 持续承载新实现开发。版本是否可发布，以对应验收报告与用户授权为准。

| 分支 | 职责 | 接收内容 |
| --- | --- | --- |
| `dev` | 开发主线 | 日常实现、修复、测试、需求和验收文档；可包含尚未形成发布候选的工作 |
| `main` | release 线、仓库默认分支 | 经批准的完整发布快照与必要发布修复；明确区分预览版与稳定版 |
| `feature/*`、`fix/*` | 可选短期任务分支 | 从开发主线派生，完成后合回开发主线 |
| `release/*`、`hotfix/*` | 可选短期集成分支 | 发布准备或 release 紧急修复，完成后整合并回流开发线 |
| `legacy/archive-*` 与 `legacy-archive-*` 标签 | 冻结历史归档 | 只读；不继续开发，不作为当前产品或验收依据 |

短期分支按任务需要创建，不要求每次小改动都增加分支，也不额外维护长期 `develop` 或 `release` 分支。当前允许直接 push，不设置仅 PR 更新限制；使用 PR 时遵守下述目标分支规则。

## 日常开发

1. 检查当前分支、工作区及相关未提交修改。保留他人的文稿与证据；工作区不适合直接切换时，在独立工作树开展任务。
2. 在 `dev` 完成普通本地修改，或从它派生短期任务分支。按改动运行必要验证，只提交明确拥有的文件。
3. 功能／修复 PR 显式选择目标 `dev`。GitHub 的默认分支仍为 `main`，不能沿用默认 PR 目标而把日常改动送入 release。
4. 推送授权与发布授权分别处理。获准同步开发分支只表示同步提交，不表示允许更新 `main` 或公开发行包。

## 发布集成

1. 在开发线上固定候选提交、版本与实际构建包，完成该发布级别要求的检查。预览版可明确列出未测范围；已确认的内容丢失或输入阻断不能仅以预览标签忽略。
2. 提供具体候选、差异、已知问题与验证报告，取得发布集成授权。准备阶段不提前移动 `main`。
3. 在干净的独立工作树从最新 `main` 创建临时发布分支，集成选定开发提交。常规发布保留 merge commit，使 release 主线的一阶历史能看出每次版本集成；不默认 squash 整条开发线。
4. 检查完整树差异、删除项、未跟踪文件和依赖锁，确保不存在旧实现残留、参考应用或私有分析产物。若集成结果改变产品输入，生成新候选并验证受影响部分；仅报告更新不重建同一产品。
5. 获准后更新 `main`。发布标签指向准确发布提交，不移动已有标签；打标签、上传归档和创建 GitHub Release 分别遵循当前授权，不由合并或推送自动触发。
6. 将 release 的集成提交或紧急修复回流 `dev`，在开发线继续后续工作。遇到新开发与 hotfix 冲突时明确解决并验证，不以整树覆盖丢弃新开发。

### 首次重写发布：衔接独立根历史

旧 `main` 与从零重写的开发线最初没有共同祖先。首次发布前保留这种状态，不为分支管理本身把未完成候选送入 release。

首次获准集成时，创建一个保留双方历史的发布合并提交：第一父提交为当时的 `main`，第二父提交为选定的开发候选；**完整文件树等于该获准开发快照**。在独立发布工作树中准备和核对，不能依赖自动合并将旧源码、旧测试或锁文件混入，也不能强推替换 `main` 历史。独立历史衔接需要一次本地准备，不能假设 GitHub 可以直接为原始两条历史创建普通比较 PR。

提交前比较发布树与候选树的 Git tree ID；不一致必须逐项解释并重新固定候选。此后把该发布合并提交回流开发线，两条活动线拥有共同祖先，后续采用普通发布合并。旧归档分支、标签与备份保持不变。

## 远端保护与自动化

仓库约定与 GitHub 强制保护是两层机制，文档落地不等于远端保护已启用。

- 两条长期活动线均应禁止删除和强推。允许直接 push，暂不设置 `pull_request` 规则、必需审阅人数或仅 PR 更新限制。`main` 的内容准入与发布授权要求继续有效。
- required checks 只绑定实际存在并稳定运行的 CI 检查名；没有 CI 时不能写入虚构的必需检查。具体检查随自动化落地再配置。
- 首次独立历史衔接在这些保护约束下进行：从 main 派生临时发布分支，生成以当前 main 为第一父提交的发布合并，再正常更新 main。已有保护阻止操作时保留规则并处理授权，不暗中绕过或关闭保护。
- 不自动推送归档、标签或全部本地分支，不使用 `git push --all`、`--mirror` 或 `--force` 来建立双线管理。

当前分支身份、远端同步和保护的实际完成情况记录在 [2026-10-24 管理记录](verification/2026-10-24-git-branch-management.md)，不从本规范推断已执行。
