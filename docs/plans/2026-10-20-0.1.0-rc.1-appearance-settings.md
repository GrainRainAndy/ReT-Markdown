# Native appearance settings

## Approved scope and design

The parent owns the table blur/render fix, browser testing, application bundle
build, and final native UI acceptance. This task owns only AppDelegate,
MenuController, new AppearancePreferences / SettingsWindowController files, and
AppearanceTests. No Git operations, web changes, app bundle builds, or agents.

Add Settings… (Command-comma) to the application menu. Its explicit native target
remains enabled with no document. Retain one lightweight AppKit settings window;
closing and reopening reuses it. The window is not an NSDocument and has one
Appearance popup with System, Light, and Dark choices.

Persist one application preference in injectable UserDefaults. Missing or invalid
values mean System. Apply restored preferences in applicationWillFinishLaunching,
before menu installation or document window creation. System sets NSApp.appearance
to nil; Light and Dark use aqua and darkAqua. Settings and document windows inherit
the application appearance, including newly created WKWebViews.

Keep the existing EditorWebView.viewDidChangeEffectiveAppearance forwarding and
the bridge's load appearance=system. No editor state, source, undo history, or PDF
appearance policy belongs in the preference implementation.

## Verification and integration

1. Capture a failing Settings menu test before implementation.
2. Test missing/invalid defaults, persistence across preference instances, forced
   native appearance, and removal of the override when returning to System.
3. Test the actual popup action and application menu validation with no document.
4. In a real WKWebView, verify startup and subsequent app overrides reach
   prefers-color-scheme; in the real EditorWebView verify appearance transitions
   preserve source revision, bytes, and undo availability. Use existing bundled
   resources without regenerating or synchronizing web output.
5. Run focused AppearanceTests and BridgeTests with the existing build/swift
   scratch path; report exact outcomes and remaining parent acceptance.

Startup/system-change risk: appearance callbacks may occur before bridge ready,
when the existing callback intentionally does nothing. The bridge's system load
must resolve the WKWebView's inherited prefers-color-scheme at startup. A system
change during bridge load may race that initial theme calculation; any required
ready-time synchronization is parent integration in EditorWebView/EditorBridge,
outside this task's ownership. Report evidence rather than adding a second flow.
